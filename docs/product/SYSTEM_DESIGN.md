# 排行榜、成就与宠物：下一步设计提纲

状态：系统方向已列入规划，以下具体玩法为建议或待决，尚未实现。不得把这些选项作为已确认需求直接开发。账号部分遵守 [用户系统规格](USER_SYSTEM.md)。

## 系统关系

记录是基础事实；同步维护归属和一致性；排行榜、成就和宠物分别按自身规则消费记录。不能让前端直接声明排名、成就已解锁或无限增加成长值。重复上传、导入、账号合并和撤销的影响须逐系统明确。

游客可以上传记录，不因未绑定而被设计成无法体验所有后续功能。哪些功能提供本地版、哪些需要联网，以及游客是否有额外限制，均需明确确认。游客云端过期清理应同时处理这些系统的关联数据。

## 排行榜：先决定“比什么、和谁比”

建议方案：自愿加入的小组周榜；公开昵称、头像及必要聚合成绩，不展示饮水明细或嘘嘘数据。优先考虑记录天数等轻量指标，不以喝水毫升数越多越好作为目标。此前“小组周榜”只是建议，全球榜、日榜、周榜的选择尚未确认。

必须决定：

- 榜单范围：全球、好友、小组，或其中一种；加入方式与退出行为。
- 指标：有效记录天数、目标完成天数或其他指标；怎样避免随意改目标获得优势。
- 周期：时区、起止时间、同分名次、结算后能否变更。
- 补记、修改、删除、离线迟到上传、导入历史数据是否计入。
- 游客参与、重复账号、绑定/合并、过期清理对历史成绩的影响。
- 是否有奖励；首版建议仅展示成绩，先不与宠物经济绑定。

规则定稿后至少提供“正常计分、同分、跨时区、删改、迟到同步、游客过期”六组示例，输入与结果必须可计算。

## 成就：先决定“鼓励什么行为”

建议方案：首批少量、可解释的里程碑，如第一次记录、累计记录若干天、首次周回顾。轻量通知，不要求用户天天连续登录；默认不使用喝水总量和嘘嘘次数作为激励。

必须决定：

- 首批成就清单、名称、说明、阈值、是否分级及具体解锁示例。
- 已有记录是否追溯、补记是否计入、删除后是否收回。
- 成就是永久纪念还是对当前有效数据的证明。
- 本地解锁与服务器确认如何区分，离线时如何展示。
- 绑定、合并、恢复备份时如何去重；规则调整影响旧成就与否。
- 成就是纯展示，还是发放宠物经验/装饰；奖励只能领一次的依据是什么。

建议先做无经济奖励的成就展示，再决定联动，避免一次引入多套数值规则。

## 宠物：先决定“陪伴方式”

建议方案：一只可命名的小伙伴，以表情、动作和轻量互动回应日常记录；不挡喝水操作，允许隐藏。此前“不漏记惩罚、不因漏记死亡、成长收益封顶”等为设计建议，需作为玩法讨论的一部分明确确认，开发者不能自行添加饥饿惩罚、交易、付费抽取等机制。

必须决定：

- 角色：物种、美术风格、是否可命名、初始领取流程。
- 核心互动：摸摸、陪伴、装饰或其他行为；首页与独立宠物页如何分工。
- 成长来源：正常记录、成就、活跃天数；是否每日封顶、如何处理漏记。
- 是否有等级、阶段形态、经验、货币、物品；第一版建议只保留一种成长进度。
- 离线表现、补记、撤销、备份、账号合并和游客过期对成长的影响。
- 动画状态、减少动态效果、低性能设备、资源大小与可关闭选项。

先确定角色与互动样稿，再制作资源和接入成长规则。不要先做素材商店或复杂数值系统。

## 建议讨论顺序与定稿方式

1. 排行榜的对象与指标：决定在线需求和公开数据。
2. 成就清单与解锁规则：决定个人长期目标。
3. 宠物角色与成长来源：决定视觉和联动。
4. 统一处理补记、导入、撤销、游客绑定/过期/合并在三个系统中的影响。

每个系统定稿后拆成独立规格，包含：目标、规则编号、界面流程、数据归属、边界示例、验收标准、明确不做的内容。由产品负责人确认后再标为“已确认”；只确定一部分时可以先实现不依赖其余决策的内容。
