## 决策状态

- **已确认**：产品负责人明确提出的要求。实现必须符合，变更必须由产品负责人决定。
- **设计基线**：已纳入文档的配套设计（包括此前讨论的技术与体验建议），在不改变已确认要求的前提下实施；不能悄悄删除。若需改动，应说明影响，由产品负责人确认涉及产品行为的变化。
- **待决**：选项或建议，尚未定案。不能将 Agent 的偏好当成最终产品规则。
- **已实现**：需要有代码和验证证据；“已确认”不等于“已实现”。

用户要求“写入文档”并不意味着此前所有候选方案都已拍板。各规格明确区分来源；开发者不得将建议改写成用户确认。

## 防止实现偏离

- 开工时列出本任务对应的规则编号和验收场景，交付时说明符合情况。无关任务不必重审全部产品规格。
- 产品负责人在当前任务中的明确新指示优先；把变更同步到规格与决策记录。发现文档互相冲突时，不自行挑选有利版本或改变产品含义。
- 技术实现细节可以自主决定；身份模型、上传范围、保留期限、计分方式、成长规则、经济系统和收费方式属于产品决策，不能由开发者自行替换。
- 待决问题只阻塞依赖它的部分，其余已明确内容继续推进。提出问题时附带选项、建议与影响，避免泛泛要求重新设计。
- 不能以“最佳实践”为由强制注册、取消游客上传、延长或缩短清理期限，也不能未经确认加入抽卡、惩罚或新社交玩法。
- 改动规格时记录日期、规则编号、变更内容、决策来源和受影响模块。只有产品负责人明确确认才能把“待决”改为“已确认”。
