# 排行榜系统：全站多指标

状态：核心范围已确认，尚未实现。统计细则待定。遵循 [产品决策规则](README.md) 和 [用户系统规格](USER_SYSTEM.md)。

## 已确认要求

来源：产品负责人明确指定全站用户、多维度多指标，以及首期只展示。

| 编号 | 规则 |
| --- | --- |
| LB-01 | 默认比较全站用户，不以朋友、小组或好友关系作为使用前提。 |
| LB-02 | 首期包含五个独立指标榜：连续记录天数、累计记录天数、目标完成天数、当日饮水总量、历史饮水总量。不能擅自缩减为单指标、替换为综合积分或只做周榜。 |
| LB-03 | 首期排名仅用于展示，不发放经验、货币、宠物成长或其他排名奖励。是否关联成长系统留待后续规划。 |
| LB-04 | 暂不开发好友、朋友小组及相关邀请/关系管理。用户量增长后再考虑，不是当前排行榜的前置依赖。 |

这组要求替代此前“小组周榜优先”“不按饮水总量排名”的建议。饮水总量榜是明确范围，开发者不得以旧建议为由删除或改成其他指标；展示的是用户记录的估计量，不是健康建议。

## 五个榜单与口径边界

| 指标 | 展示单位 | 已明确含义 | 实现前必须确定 |
| --- | --- | --- | --- |
| 连续记录天数 | 天 | 衡量连续记录 | 当前连续还是历史最长；今天未记录时是否保留截至昨天的连续；断签与补记影响 |
| 累计记录天数 | 天 | 衡量累计记录的日期数，同一天不重复加天数 | 哪类记录构成有效记录；旧数据、导入和删改的处理 |
| 目标完成天数 | 天 | 衡量完成饮水目标的日期数，同一天不重复加天数 | 历史累计还是特定周期；按当天哪个目标判定；关闭目标、当天改目标和补记的处理 |
| 当日饮水总量 | ml | 当天饮水记录的累计量 | 全站统一日期/时区还是用户本地日期；同步延迟、改时间和跨日处理 |
| 历史饮水总量 | ml | 历史饮水记录的累计量 | 是否包含账号创建前记录、备份导入和合并数据；删除后的回算 |

具体建议（尚未确认）：连续榜使用当前连续天数，目标完成天数使用历史累计，各榜按数值降序展示。这些建议及所有边界必须在实现前定稿，不能由 Agent 默认拍板。

## 配套设计基线

- 各指标独立展示，不能未经确认混合成总分。可采用页签或指标选择器切换，视觉布局可在原型阶段比较。
- 使用服务端确认的数据计算排名，不信任客户端直接提交排名或最终分数；同一记录同步重试不能重复计入。
- 公开字段仅覆盖榜单所需的昵称、头像和聚合成绩；不因全站榜就公开联系方式、饮水时间线或嘘嘘明细。
- 游客拥有可上传的身份；不得擅自增加“绑定后才可参与”的门槛。公开参与及退出设置、零记录是否展示等细则仍需确认。
- 未同步的本地变化不能伪装成服务器排名；加载、无数据、离线和同步延迟有清晰反馈，不以虚构用户填充正式榜单。
- 绑定时保持原 ID，不能重复上榜；账号合并、游客到期清理和账号删除须与用户生命周期规则一致。
- 展示饮水总量不等于鼓励追赶饮水量；首期不设置超量奖励或“再喝多少超过某人”的催促文案。

## 剩余决策

1. 有效“记录日”是否只计饮水，还是包含嘘嘘；连续天数采用当前还是最长连续。
2. 每个榜的周期、全站时间边界和时区；不自行将全部榜单改成日榜、周榜或月榜。
3. 历史目标保存方式与目标修改生效时间，避免按当前目标重算所有历史日期。
4. 补记、编辑、删除、离线迟到同步、导入和账号合并分别怎样计入。
5. 同分采用并列排名还是其他规则；零值用户、展示人数、分页与“我的排名”。
6. 全站榜的公开说明、参与/隐藏/退出选项，游客昵称的基础管理方式。
7. 刷新频率、异常记录校验、清理后历史成绩的处理。异常值规则需明确，不能偷偷封顶或删减真实统计。

## 验收框架

规则定稿后补充可计算样例，并至少验证：

- 五个榜均可切换，指标与数据独立，没有好友功能依赖、综合积分或奖励发放。
- 同日多条记录不重复增加记录天数；饮水总量按有效记录累计。
- 连续天数跨零点、缺一天、补记后按已定规则变化。
- 目标变更、关闭目标和历史日期的目标完成判定符合目标快照规则。
- 同分、跨时区、迟到同步、编辑删除、备份导入和重复提交处理一致。
- 游客绑定不产生第二个身份；游客过期后按用户规格移除云端榜单关联。
- 公共接口不泄露私密字段，断网时不将本地成绩称为实时排名。
